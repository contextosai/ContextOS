# Learning from Agensh

Study date: 2026-10-25. Local source: `/opt/genai/Agensh`, commit
`0468a3e6a58b51dc2b84871fcaa0df22b0d1033e`. Paper:
[Agensh: Scaling Organizational Intelligence to 1,024 Agents](https://arxiv.org/pdf/2609.26781).
The user's implementation priority is decentralized task coordination.

## What transfers

The paper's cooperation loop is gather context, claim work, act, verify, integrate.
Its useful architectural separation is between the individual agent's loop and
infrastructure that helps peers cooperate. That fits ContextOS's existing choice
to govern framework-owned agent loops rather than replace them. Claims, messages,
and shared findings are coordination inputs; they cannot confer tool authority.

The paper reports improvement on five difficult software reconstruction tasks,
including a 1,024-worker experiment on one task. Those results do not establish
ContextOS performance, cost efficiency, business safety, or general workload quality.

The following implementation details were checked in the local repository, rather
than inferred from the paper's high-level diagrams:

| Mechanism | Source | Lesson and limit |
|---|---|---|
| Equal worker protocol | `prompts/agents.txt` | Peers choose tasks, announce scope, verify, merge, and publish. Roles emerge from cooperation; there is no task-assignment algorithm to transplant. |
| Typed shared context | `board-service/shared_lessons.py`, `verifier.py` | FACT, OBSERVED, FAIL, CLAIM and PATCH_SUMMARY make reusable knowledge concise. Text checks on evidence do not run tests or establish truth. |
| Claim expiry | `SharedLessons.note`, `_is_expired_claim` | Claims expire from the recent view, but they are advisory announcements. They do not atomically exclude another worker or fence an expired claimant. |
| Recent view and history | `shared_lessons.py`, `main.py:get_grep`, `unfold.py` | Recent memory is capped at 2,000 entries; persistent history remains searchable. Short summaries and expandable detail avoid flooding every prompt. |
| Task-local patch lifecycle | `SharedLessons._admit` | Later summaries replace an author's recent candidate for a work label; a matching FAIL invalidates it. History remains in MySQL. This is useful revision tracking, not independent verification. |
| Durable event dispatch | `mini-router/src/state.ts`, `dispatcher.ts` | Deduplicate ingestion, serialize each worker's turns, acknowledge completed turns, bound retries, and recover interrupted sends. Recovery can redeliver; effects still need their own idempotency. |
| Mid-turn delivery | `mini-router/mcp-notice-shim.cjs`, `main.py:get_pending/post_shown` | A short lease reduces duplicate drains; acknowledgement follows emission. Delivery happens at infrastructure tool returns, not arbitrary process interruption. Emitting a notice does not prove an agent acted on it. |
| Board visibility | `main.py:_authorize` | Membership is checked using supplied worker identity on a private network. ContextOS must use authenticated principals and protected run lineage. |
| Worker recovery | `agent/acp-bridge.py`, `archive.py` and their component guide | Preserve native sessions and sealed workspace archives. ContextOS checkpoints cover orchestrator state, not a full filesystem or native-model session. |
| Bounded prompt backlog | `mini-router/src/group_messages.ts` | Large group batches spill to a JSONL file, keeping only a bounded recent window inline. Omitted context must remain retrievable. |
| Experiment versus release | `REPRODUCE.md:Experimental conditions and release differences` | The public stack differs from historical experiments in harness, cleanroom and shutdown details. Teams use staggered activation and permissive integration settings. Record versions and timing before comparing outcomes. |

No Agensh code is copied into ContextOS. The proposed extension uses ContextOS's
existing stores, clock, authentication, audit and clients.

## Chosen direction

Add an optional work board shared by one admitted root run and its verified
delegation descendants. Peers discover ready tasks and compete for a time-limited,
atomic claim. They renew, release, or report completion with evidence references.
Task revisions and lease epochs atomically fence changes to work ownership;
separate run lifecycle checks have a documented race boundary. Access also binds
the authenticated caller to its admitted worker principal. Task completion is a
worker report, never an independent quality or authorization verdict. Lease expiry
does not establish that earlier effects are safe to repeat. The root can still be
admitted once and hand execution to peers without centrally scheduling every task.

The first bounded board favors a single compare-and-swap document for atomic task
dependencies, claims, and erasure. It must declare its capacity and contention
limits. A future per-task partition should be justified by coordination benchmarks,
with a deliberate solution for consistent dependencies and erasure. A 1,024-agent
claim is out of scope until measured.

The independent builder review identified four requirements to settle before code:
bind participant identity beyond tenant/generation; separate task CAS guarantees
from lifecycle races; tombstone even an absent board before removing retention's
ReplayCase index; and preserve effect-reconciliation and child-output acceptance
boundaries when a task is reassigned. These are incorporated into the
[proposed design](../superpowers/specs/2026-10-25-peer-task-coordination-design.md).

## Follow-up order

1. Durable task board, conditional claims, recovery, HTTP clients and offline demo.
2. Typed findings with explicit provenance and invalidation; bounded recent view
   plus paginated searchable history.
3. Durable notices with peek/ack separation, delivery leases and framework adapters.
4. Peer integration protocol with independent evidence review and completion gates.
5. Multi-replica PostgreSQL coordination benchmarks, including contention, stale
   lease recovery, context volume and useful completed work per unit cost.

## Implemented increment

The approved task-coordination increment is implemented: see the [user guide](../PEER_COORDINATION.md), [ADR-0006](../adr/0006-peer-task-coordination.md), and [local demo](../../examples/peer-coordination/README.md). The full repository gate passed with PostgreSQL enabled, including cross-connection persistent claim coverage. An independent final review found no actionable defects. These checks establish the tested coordination behavior; they are not a throughput benchmark or a replication of Agensh's organizational experiments. Shared findings, notices and workspace integration remain follow-up work.

Follow-ups 2 and 3 are now implemented as [shared findings and peer notices](../FINDINGS.md):
typed claims and observations whose basis the gateway takes from its operation ledger,
falsification only by the author or by citing an observation published to refute it, suspect marking of
dependents, and notices peeked on each member's tool results until acknowledged. One
bounded document per root replaces the study's recent view plus searchable history;
framework adapters beyond MCP and the REST metadata remain open.
