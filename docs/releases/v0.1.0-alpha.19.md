# ContextOS 0.1.0-alpha.19

The nineteenth alpha of ContextOS. It carries out the identity and evidence milestone
that followed the
[enterprise problems research](../research/2026-11-08-enterprise-agent-problems.md).
Security reviews of agents ask two questions the previous release left open: who was
the agent acting for, through which other agents, and can the organization show a
reviewer what the controls did. This release answers both from the gateway's own
records.

## What changed since 0.1.0-alpha.18

**Who an agent acts for**

- Multi-hop delegation: the nested actor claims of a delegated token (RFC 8693 `act`
  within `act`) are read as a chain, current actor first, and kept on the run. A
  delegated child run inherits its parent's chain. `run_admitted` records the chain's
  `depth` and `chain_digest`, never the identities in it.
- Kill switch: `user` stops every run acting for a user, and `delegation` stops one
  exact chain by its digest. `principal` now also stops runs whose chain names that
  principal. Tower's kill switch offers both new kinds.
- Privilege intersection: a capability can list `required_user_roles`. Its effects
  then run only for a run acting for a user who holds one of those roles, as the
  delegated token says (`[oidc.delegation] user_roles_claim`). Otherwise the call is
  refused before anything is sent and audited as `privilege_refusal`. Capabilities
  without the field are unchanged.
- Guides for [Microsoft Entra ID](../integrations/entra-id.md) and
  [Okta](../integrations/okta.md), with conformance tests that admit runs from tokens
  shaped like each provider's.

**Tower for an organization**

- Single sign-on (`[sso]`): people sign in with the organization's OpenID Connect
  provider, and `[[sso.groups]]` maps groups to Tower roles and teams. A person in no
  mapped group is refused. Tower exchanges the authorization code itself, so a client
  secret never reaches the browser. API keys keep working.
- Pinned audit history: Tower keeps the last entry it verified from each runtime. If,
  after Tower restarts, a runtime's chain no longer passes through that entry, the
  source is marked broken (`history_rewritten` or `history_truncated`) instead of
  being read afresh.

**Evidence a reviewer can use**

- `ctx evidence-pack --framework soc2|iso42001|eu-ai-act|owasp-agentic` builds a
  review folder, only from an audit export that verifies. It holds the export and
  keys, a control map that counts each control's audit events over the period, a
  coverage statement saying what the evidence does and does not cover, and a manifest
  with every file's digest. The same export gives the same folder.
- `ctx init-tool --preset github|database|crm` labels a drafted manifest's information
  flow for that tool set. With the default policy, an agent that read an issue and
  then private code is refused when it opens a pull request, and personal data
  read from a CRM cannot be emailed out.
- `ctx manifest` returns review `notes`: effectful capabilities without an amount or
  resource, names that look destructive on capabilities declared reversible, and
  effects that may not repeat without an intent key.

**Examples**

- `examples/consequential-tools` replays a support agent's recorded refunds through
  the starter profile: a live-order refund from staging, the same refund from a second
  run, and a breached daily cap are each refused.
- `examples/postgres-drill` phase 6 races the same refund from three processes under
  fresh runs and keys on PostgreSQL; exactly one is paid, including after a sender is
  killed mid-flight.

## Upgrading

- **Delegated tokens are checked for their chain.** A token whose actor chain is longer
  than `[oidc.delegation] max_chain` (default 4, at most 16), names an actor twice, or
  names the user as an actor is rejected. Raise `max_chain` before upgrading if your
  tokens nest deeper.
- **`principal` revocations reach further.** They now also stop runs whose delegation
  chain names the revoked principal, not only runs it admitted.
- **New audit data.** `privilege_refusal` is a new entry kind, `revocation` entries
  may carry the kinds `user` and `delegation`, and `run_admitted` gains `delegation`.
  Consumers that switch on audit kinds should expect them.
- **Presets are a starting point, not only a tightening.** The GitHub preset labels
  issue text as public, so a read followed by a comment asks for approval rather than
  being refused. Review preset labels like any other field.
- **Rust API.** `Gateway::admission_revoked` takes `AdmissionTargets`, and
  `run_targets` returns a `Vec`. `VerifiedUser` gains `actors`.
- Tower keeps its pins in its existing store; no migration is needed. No configuration
  key, API route or storage format is removed.

## Known limits

- Microsoft Entra ID's on-behalf-of tokens carry no RFC 8693 actor claim, so they do
  not bind the user to the run. The Entra guide lists the options.
- `required_user_roles` trusts the roles claim of the delegated token; it does not
  look the user up in the directory.
- A Tower pin cannot be reset in place. To accept a runtime's rewritten history,
  remove the source and add it again under a new id.
- Estimated spend still settles as estimated, and only calls routed through the
  gateway are governed. An agent that holds a credential to the tool directly
  bypasses every control here.
