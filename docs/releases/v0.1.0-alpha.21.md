# ContextOS 0.1.0-alpha.21

The twenty-first alpha of ContextOS. It adds evaluation gates for agent releases and
acts on an external review of alpha.20. That review found three things worth fixing.
A verified conformance report could not be tied to a suite the deployment accepts.
Evidence packs said a control was "evidenced" when its events had merely occurred. And
the release archive's pack checks needed an override to find `ctx`.

## What changed since 0.1.0-alpha.20

**Accepting a conformance claim**

- `[[conformance.accepted_suites]]` pins, per tenant and workflow, the one suite this
  deployment accepts (type, id, version and digest) and the cases it must show
  passed. It also states whether a failed optional control blocks acceptance:
  `optional_failures = "block"` or `"disclose"` is required and has no default.
- `POST /v1/conformance/assess` returns `acceptance` beside the assessment, which is
  unchanged. It is `accepted` only when the assessment passed and the report names
  exactly the pinned suite. Every listed case must have passed under a required
  control or as a utility result, where the assessor checked its evidence. Under
  `block`, no optional control may have failed. Otherwise it is `not_accepted` with
  reasons, or `no_policy` when none is configured. `optional_failed` lists failed
  optional controls either way, since the assessor's outcome can be `passed` while one
  failed. The acceptance is audited with the outcome (GUIDE §10).
- List the regressions the workflow relies on as required cases, such as a retry
  reclaiming an intent another run holds (fixed in alpha.20).

**Evidence packs say what counts show**

- `ctx evidence-pack` marks a control whose event kinds occurred in the period as
  `events_recorded`, not `evidenced`. `coverage.md` says that a count shows the
  control acted at least once. It does not show that every required behavior was
  tested, that the control is configured everywhere, or that it is effective. The pack
  is an audit export with a control index, not a test result or a compliance finding.
  The pack version is now `contextos.evidence_pack.v2`.

**Evaluation gates**

- `ctx trials` turns run evidence into per-trial pass or fail. A trial passes when its
  run completed, every owed outcome was witnessed and scores meet the criteria.
  `ctx reliability-gate` gates a release on pass^k per case. It uses a paired
  non-inferiority interval that can answer `inconclusive` and reports the drop the
  suite could detect. It also checks path convergence, `must_pass` cases and floors
  (GUIDE §5).
- Tool-call evaluations: `POST /v1/runs/{run_id}/operations/{operation_id}/evaluations`
  (scope `evaluate`) records an independent evaluator's verdict on one governed call.
  It uses the fields of the OpenTelemetry `gen_ai.evaluation.result` event, signed,
  listed in the evidence bundle and counted by `ctx trials` (GUIDE §7).
- Evaluator calibration: `ctx calibrate` checks a judge against human labels (TPR,
  TNR, Youden's J, Cohen's kappa). `[guards.evaluator_calibration]`, off unless set,
  refuses scores and evaluations from evaluator releases without a record meeting the
  deployment's floors (`evaluator_uncalibrated`).
- The Python and Node clients gain `evaluate_operation` and `evaluateOperation`.
  `examples/evaluation-loop` shows a calibrated evaluation platform judging a
  candidate agent's tool calls, and the reliability gate turning its verdicts into a
  release decision.

**Release archive**

- `examples/support-refund/check_packs.sh` and the pack-authoring skill's
  `check_pack.sh` find `ctx` in the archive's `bin/` (then `CONTEXTOS_BIN`, a source
  build, `PATH`). Before, they defaulted to an absent `target/release/ctx`. The README
  lists the three archive commands, and the release gate runs each from an unpacked
  archive with no overrides:

  ```sh
  ./examples/support-refund/check_packs.sh
  ./examples/shared-guarantees/run.sh
  ./bin/ctx audit-verify --entries receipts/shared-guarantees/entries.json \
      --keys receipts/shared-guarantees/keys.json
  ```

## Upgrading

- **Evidence packs (breaking).** Readers of `controls.json` or `manifest.json` should
  expect `events_recorded` where alpha.19 and alpha.20 wrote `evidenced`, and the pack
  version `contextos.evidence_pack.v2`. Nothing else in the pack changed.
- **Conformance responses** gain an `acceptance` object. Without
  `[[conformance.accepted_suites]]` it is `no_policy`; treat that as not accepted.
  The assessment's `outcome` and other fields are unchanged.
- Evaluation features are opt in. `[guards.evaluator_calibration]` is off unless set,
  and the evaluations route needs a key with the `evaluate` scope.
- No configuration key, API route or storage format is removed.

## Known limits

The known limits of alpha.20 apply unchanged. In addition:

- Whether a failed optional control should block an assessment's overall outcome is
  still open in the specification. `optional_failures` makes each deployment state
  its own rule; the assessor's behavior is unchanged.
- Required case IDs are the deployment's. No published suite yet emits a case for the
  alpha.20 intent-claim retry race, so a policy naming one will report it missing
  until the suite does.
- Shared limits and recovery have been exercised against local synthetic providers
  only. No external-provider sandbox pilot has been completed.
