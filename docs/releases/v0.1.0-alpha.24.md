# ContextOS 0.1.0-alpha.24

The twenty-fourth alpha of ContextOS fixes what an independent review of alpha.20 to
alpha.23 found. The review read the guards, privacy, quarantine, break-glass,
pack-signing and SVID code added in those releases and found no blocker, but nine
issues: two of them hid worse bugs, which this release also fixes. Each fix has
regression tests and an updated threat-model entry (T52, T55, T62, T64, T66).

## What changed since 0.1.0-alpha.23

**Fixed**

- **Usage ceilings count measured usage.** In alpha.23 a ceiling was charged what each
  call reserved; usage a metering gateway measured above the reservation reached the
  run's budget but not the shared ceiling, so a caller that reserved too little could
  pass it. Measured overage is now added to every covering ceiling, even past its
  limit, after which the ceiling refuses for the rest of its window.
- **Busy ceiling windows.** A ceiling's ledger kept every settled call, so after 1,024
  model calls in one window every further call was refused as
  `usage_ceiling_reached`. Settled calls are now compacted. A store failure part-way
  through holding several ceilings releases the holds already taken.
- **A frequent data subject no longer fails admission.** The subject index was one
  document per subject, and at about 10,000 runs it outgrew the store's document
  bound: every further run naming that subject failed admission with
  `503 store_unavailable`. The index now grows in pages of 5,000 runs, up to 1,000,000.
- **Holds by subject cover every indexed run.** Each run now records its own subjects'
  digests, so a legal hold by subject covers it however large the subject's index is.
- **Quarantine on every replica.** A replica that could not write a new quarantine
  after repeated store conflicts kept serving the drifted tool until its next check; it
  now refuses it meanwhile.
- **Break-glass expiry** is compared as a time rather than as text. An expiry that is
  not a valid timestamp counts as expired.

**Added**

- `[guards] quarantine_releasers`: the principals that may release a quarantined
  upstream tool. A quarantine protects every tenant the runtime serves, so in a
  multi-tenant deployment another tenant's `control` principal should not lift it;
  others get `403 quarantine_release_forbidden`, and `--check-config` warns when several
  tenants are configured without the list.
- `[privacy] subject_key_env`: digest data subjects with HMAC-SHA256 under a deployment
  key (`hmac-sha256:…`). Without it the digest is plain SHA-256: a pseudonym, which a
  guessed account number or e-mail address can be checked against. With
  `match_unkeyed_subjects`, runs indexed before the key stay findable while you
  migrate, and their unkeyed digests never reach the audit chain.
- Release evaluations: `min_cases` and `suite_versions` per rule, so a one-case pass or
  an older suite version cannot satisfy a gate.

**Documentation**

- What four controls trust and do not enforce: model allow-lists are advisory for
  agents whose calls bypass a metering gateway; break-glass and legal holds need no
  second person (the check is the audit chain and Tower's review); change windows
  shift with daylight saving; and an audit entry can exist for a hold or grant whose
  store write lost a race, so read state from the store.
- The alpha.22 and alpha.23 notes now scope two claims: usage ceilings bound
  reservations, and holds and erasure by subject cover indexed runs only.

## Upgrading

- **Usage ceilings may refuse sooner.** Measured usage above reservations now counts,
  so a deployment whose callers under-reserve will reach its ceilings earlier than on
  alpha.23. Check ceilings against measured spend (`ctx chargeback`, Tower's spend)
  before upgrading.
- **No store migration is needed.** Subject index pages and per-run subject records use
  the existing `subject_index` document kind, and the first page keeps its key. Run
  `contextosd --migrate` as usual; CI checks an upgrade from an alpha.23 PostgreSQL
  store. Runs indexed before this release have no per-run record and are found
  through the index as before.
- **Keyed subject digests are opt in.** Set `subject_key_env` before the first indexed
  run. On a deployment that already indexed runs, also set
  `match_unkeyed_subjects = true` until those runs are erased or past retention. Keep
  the key with your other secrets: without it, a person's runs cannot be found by
  their identifier.
- **Rust API.** `EvaluationRule` gains `min_cases` and `suite_versions` (it now derives
  `Default`; use `..EvaluationRule::default()`). `GuardsConfig` gains
  `quarantine_releasers`, `PrivacyConfig` gains `subject_key_env` and
  `match_unkeyed_subjects`, and `DispatchSetup` gains `subject_key`. Struct literals
  need the new fields.
- Everything else is opt in. Run `contextosd --check-config`.

## Known limits

The known limits of alpha.23 apply, except those fixed above. In particular:

- **Self-reported usage** counts against a ceiling at the reservation; only a metering
  gateway's measurement adds overage.
- **Fixed windows.** A burst that straddles a ceiling's window boundary can use up to
  twice the limit within one window's length.
- **Subjects** are indexed only for runs admitted after `[privacy] subject_pointers`
  was configured.
- **No second person** is required to open break-glass or to release a hold; keep
  those credentials apart from the people who review them.
- **Change windows** use fixed UTC offsets; time-zone names are not supported.
- **Planned, not built:** a timeout scenario in the Failure Lab, an agentgateway
  ext_authz backend, OPA/Cerbos policy import, `ctx adapter-check`, and GenAI
  token-usage metrics. gRPC stays deferred.
