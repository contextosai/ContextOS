# ContextOS 0.1.0-alpha.22

The twenty-second alpha of ContextOS. It widens what ContextOS governs from the effect
of one tool call to the lifecycle of an agent: who it is, what it may do, what data it
touched, who approved it, and how a person can stop it, review it or erase what it
holds. Refunds stay one reference workflow among several.

Every addition extends a mechanism that already existed (the audit chain, revocations,
runtime guards, the approval contract, Tower's signed journal) and none weakens a core
guarantee: authorization before the action, shared limits across agents and runs, held
effects on unknown outcomes, signed hash-chained evidence verifiable offline,
digest-bound approvals, tenant isolation and fail-closed behaviour. Each has a
threat-model entry (T45 to T58) and regression tests.

## What changed since 0.1.0-alpha.21

**Inventory and lifecycle (Tower)**

- An inventory of every agent, capability, adapter, model and owning team, with first
  and last seen, environments, risk tier and whether it is declared, as a page, JSON or
  CSV, derived from verified evidence; `ctx inventory` builds it offline from an audit
  export and refuses one that does not verify.
- Shadow findings: tools an agent called that no pack gives it, and models its
  declaration does not list; `ctx inventory --fail-on-shadow` for CI.
- An approved lifecycle: proposed, approved, active (pilot, production, deprecated),
  suspended, retired. Each move is approved by a second person and journalled;
  suspending or retiring revokes the agent on every runtime Tower controls.

**Risk tiers and policy**

- `[guards.risk_tiers]`: each capability is low, limited, high or prohibited; high needs
  an approval of the exact action, prohibited is always refused, unclassified counts as
  high.
- `[[guards.change_windows]]`: freezes and out-of-hours windows, decided on the server
  clock.
- `ctx simulate`: what a candidate pack would decide differently on recorded runs, as a
  JSON and Markdown report; `--fail-on-widening` for CI.
- Ready-made control packs in `deploy/profiles/controls` for spend and rate limits, data
  egress, personal data, destructive actions, environment separation, change freezes
  and human-in-the-loop approvals.

**Data governance**

- Data categories (`pii`, `phi`, `pci`, `secrets`) on tool outputs, tracked per run, and
  boundaries that say which tools, vendors and regions each may leave through.
- Legal holds that keep runs from erasure and retention, and deletion requests by data
  subject; identifiers are kept only as digests, and the chain still verifies.
- A reference result screener (`examples/result-screening`), pattern based and off by
  default.

**Identity and access**

- Every decision of a delegated run records its delegation path (depth and digest) and
  run lineage.
- X.509 SVIDs: with mutual TLS, a client certificate's SPIFFE ID narrows the agent a
  caller may admit runs as.
- Access reviews in Tower: grants used, unused and never used, stale delegations,
  dormant agents, expiring waivers and reviews, with a digest-bound attestation.
- Break-glass: a separate credential lifts change windows and open circuit breakers,
  nothing else, for named capabilities for at most an hour, with every call audited and
  a mandatory review in Tower.

**Oversight**

- The kill switch at four scopes: agent, tool, tenant and a new `global` revocation for
  every tenant of a runtime, held by named principals.
- Approval analytics: denials are audited; Tower shows denial and override rates
  (approvals of actions a runtime guard had flagged).
- A reference approval relay for Slack, Teams and e-mail with signed callbacks,
  escalation tiers and delegation, tested end to end against the runtime.

**Release engineering**

- CI gates every release on an upgrade from the previous release's PostgreSQL store and
  packs, and on README's Quickstart run as written on fresh Linux and macOS runners.
- `url` 2.5.9 fixes RUSTSEC-2026-0592; dependencies updated.

## Upgrading

- **Tower lifecycle approval (breaking).** With `[governance] lifecycle_approval` (on by
  default), a new declaration must be `proposed`, and changing `lifecycle` through
  `PUT /api/agents/{key}/declaration` answers 409; use lifecycle requests. Existing
  declarations keep their stage. Set `lifecycle_approval = false` while scripts move.
- **Rust API.** `information_flow::RunLabels` has a `categories` field; `ErasureError`
  gains `Held`; the retention sweep's `Swept` gains `held`. Struct literals need the new
  fields.
- **Erasure.** `POST /v1/runs/{id}/erase` answers `409 legal_hold` for a held run.
- Everything else is opt in: risk tiers, change windows, data boundaries, legal holds,
  subject pointers, break-glass, SPIFFE mapping and the global kill switch do nothing
  until configured. Run `contextosd --check-config` on your configuration.
- No storage migration is needed beyond `contextosd --migrate` as usual; the upgrade gate
  checks an alpha.21 PostgreSQL store.

## Known limits

The known limits of alpha.21 apply unchanged. In addition:

- Data categories and boundaries are declared metadata: a tool that returns personal
  data without declaring it is not caught. The runtime never inspects content.
- The approval relay and result screener are references: in-memory state, pattern
  matching. Measure them before relying on them.
- SPIFFE identities need mutual TLS terminating at contextosd; behind a TLS-terminating
  proxy keep JWT-SVIDs.
- Change windows use fixed UTC offsets; daylight saving is not modelled.
- Legal holds and deletion requests by data subject cover only runs in the subject
  index: runs admitted after `[privacy] subject_pointers` was configured, and about
  10,000 per subject (admission of further runs naming that subject fails). Holds by
  run or tenant are not affected.
- Not in this release, planned for alpha.23: the governance dashboard, incident cases,
  behaviour flags, evaluation-gated promotion, model allow-lists, cross-run model
  budgets, chargeback, quarantine for drifted tools, signed packs, Sigstore-signed
  release assets, compliance coverage per control, the one-command audit pack, SIEM
  formats, an agentgateway ext_authz backend and OPA/Cerbos policy import. A timeout
  scenario in the Failure Lab is planned without a date. gRPC stays deferred.
