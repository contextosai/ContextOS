# Agent Failure Lab

A static page for people deciding whether their agents need a gateway in front of tools
that move money. A support agent has a refund tool; the visitor picks one of five
failures and steps through it, comparing the same attempts sent straight to the payment
API with the same attempts sent through ContextOS. Each one takes about a minute and
needs nothing installed.

| Failure | What the gateway does | Link |
|---|---|---|
| The provider's answer is lost; the agent retries and the ticket is redelivered | Holds the unknown outcome, refuses the repeat from any run, settles on cited evidence | `#lost-response` |
| The agent refunds more than the customer asked for | Checks every call against the task the run was started with | `#over-reach` |
| The agent splits a refund that needs approval | Requires approval for each call; an approval covers one exact action | `#approval` |
| Small refunds across runs pass a daily limit | Keeps one limit per agent across runs | `#daily-cap` |
| The agent loops | A circuit breaker refuses, revokes the agent, and its next run is not admitted | `#runaway` |

Open `index.html` in a browser, or serve this directory as static files:

```sh
python3 -m http.server -d lab 8000   # then http://127.0.0.1:8000
```

| File | |
|---|---|
| `index.html`, `lab.css`, `lab.js` | The page. No dependencies, build step or third-party requests. |
| `words.js` | The words around each recorded step, keyed by scenario and step name. |
| `story.js` | The recording it plays back. Generated by [examples/failure-lab](../examples/failure-lab); do not edit. |

Below the tally, a static table maps each failure onto cloud and SRE, finance and ERP,
regulated data, and coding fleets, since the mechanics do not depend on the tool;
[docs/USE_CASES.md](../docs/USE_CASES.md) links the controls for each.

`#lost-response/3` opens a failure at its third step and `#lost-response/end` at its
result.

Everything the page shows about the gateway (answers, amounts, balances, audit entries,
configuration) comes from `story.js`. Beside the gateway the page shows one or two
baselines without it, including the strongest one we could think of for each failure
(idempotency keys, or a threshold check in the tool), and each result says what that
baseline does and does not cover. "Not authorised" money is what a side paid twice,
beyond what was asked, without a required approval or past a configured limit; the
recorder computes it per ledger entry.

The audit log of each failure can be saved from the page and verified offline with
`ctx audit-verify`. The page then points to
[replaying your own refund calls](../examples/replay-refunds).
