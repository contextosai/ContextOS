# ContextOS 0.1.0-alpha.6

The sixth alpha of ContextOS: shared business limits for AI agents, enforced before
mediated tools act, with signed evidence of confirmed and unresolved effects.

This release is for evaluation and early integration. APIs and storage formats may
change. Passing the synthetic conformance and regression suites does not certify a
deployment or establish that a provider's effects are safe to repeat.

## What changed since 0.1.0-alpha.5

- **Alerts and a dashboard for on-call.** `prometheusRule.enabled` installs alerting
  rules, each with a runbook in `docs/INCIDENT.md`:
  - shared-guarantee saturation and receipts near the cap;
  - unknown outcomes, held effects aging, conflicting facts;
  - blocked-dispatch spikes, saturated guards and enforced revocations;
  - upstream drift, failing notifications, escalations waiting;
  - server errors.

  The leader replica now publishes gauges for held effects by state and the oldest
  hold's age, without tenant labels. A hold older than 15 minutes is logged once with
  its tenant for your SIEM. `deploy/grafana/contextos-governance.json` is the matching
  dashboard.
- **Agents bound to their credentials.** `[guards] agent_binding` checks a run's
  declared agent against the agents its credential is issued for: an OIDC
  `agent_claim` (SPIFFE JWT-SVIDs with `sub`), optionally mapped, or an API key's
  `agent_ids`. `observe` counts and records mismatches; `required` refuses them.
- **MCP authorization.** With `[server] public_url`, MCP hosts discover where to get a
  token from OAuth protected resource metadata (RFC 9728) named in every `401`. Adapters
  can get provider tokens with the client credentials grant (`[adapters.oauth]`).
- **Upstream drift detection.** Pin a capability to the upstream MCP tool definition
  you reviewed (`upstream_tool_digest`; print it with `contextosd --pin-mcp-tools`).
  While the server's definition differs, calls are refused with
  `upstream_tool_drifted`.
- **Escalation notifications.** `[[notifications]]` webhooks receive signed
  CloudEvents for escalations opened and resolved. They are delivered from the audit
  chain, so none is lost or invented. `examples/notify/` relays them to Slack and
  PagerDuty.
- **Result screening.** `[providers.result_screening]` lets your classifier withhold
  or redact a tool's output before the agent sees it. It fails closed and is audited.
- **Approval step-up.** `[guards.approval_step_up]` makes large approvals count only
  after every approver's recent strong sign-in, as reported by your approval service.
- **Scope.** [What ContextOS does not govern](https://github.com/contextosai/ContextOS/blob/v0.1.0-alpha.6/docs/SCOPE.md)
  lists what falls outside the effect boundary and where to add the control.

The full list is in the [changelog](https://github.com/contextosai/ContextOS/blob/v0.1.0-alpha.6/CHANGELOG.md).

## Upgrading from 0.1.0-alpha.5

No storage migration is needed. Without the `contextos.enterprise` profile nothing
changes behaviour: agent binding defaults to `observe` and upstream pins are optional,
with warnings from `--check-config`. With the enterprise profile, two changes can stop
startup:

- **Agent binding is required.** Startup refuses an OIDC issuer without
  `agent_claim` and an `admit`-scoped API key without `agent_ids`, and admission
  refuses a run whose declared agent its credential does not name
  (`403 agent_not_bound`). Add them, or set `[guards] agent_binding = "observe"` and
  watch `contextos_agent_binding_mismatches_total` reach zero before switching.
- **Effectful MCP capabilities must be pinned.** Run
  `contextosd --pin-mcp-tools <config>` against the current servers, review the
  digests and add `upstream_tool_digest` (and `upstream_description_digest`) to each
  capability manifest.

Rust embedders: `ApiKey`, `Caller` and `CapabilityManifest` gain fields, and the
`Adapter` and `CredentialBroker` traits gain methods with defaults.

## What is included

- `contextosd`: the governed tool gateway, protected state, admission, approvals,
  budgets, executor fencing and conservative reconciliation of unknown outcomes.
- Shared numeric resource ceilings across independent agent runs and replicas using
  one protected store. Pending and partial effects continue to consume capacity.
- `ctx`: offline validation, compilation, audit verification and release-gate tools.
- `towerd` and the prebuilt Tower UI: fleet evidence, role-based governance, reviews,
  guardrails and waivers. Optional AI assistance is off in the local example.
- An optional peer task board with leased claims and recovery. Task reports are
  advisory; they do not authorize effects or prove that work was completed safely.
- The Python HTTP client, documentation, licenses and dependency notices, plus local
  examples for shared guarantees, refunds, agent loops, peers, metering and Tower.

Framework integrations and native Python/Node/WASM bindings are available in the
source tree. This release does not publish packages to PyPI, npm or crates.io.

## Verify and try it

Download the archive and checksum for your platform. For example, on Apple Silicon:

```sh
asset=contextos-v0.1.0-alpha.6-aarch64-apple-darwin.tar.gz
curl -fLO "https://github.com/contextosai/ContextOS/releases/download/v0.1.0-alpha.6/$asset"
curl -fLO "https://github.com/contextosai/ContextOS/releases/download/v0.1.0-alpha.6/$asset.sha256"
shasum -a 256 -c "$asset.sha256"
gh attestation verify "$asset" --repo contextosai/ContextOS \
  --signer-workflow contextosai/ContextOS/.github/workflows/release.yml \
  --source-ref refs/tags/v0.1.0-alpha.6
tar xzf "$asset"
cd contextos-v0.1.0-alpha.6-aarch64-apple-darwin
./bin/contextosd --version
./examples/shared-guarantees/run.sh
```

The provenance check uses an authenticated GitHub CLI. The shared-guarantees demo
uses synthetic local services, requires no model key or payment account, races two
agents against one ceiling, reconciles pending exposure and verifies the audit.
Try `./examples/support-refund/run.sh` and `./examples/tower/run.sh --serve` next.

The release also includes per-crate CycloneDX JSON inventories of the locked Rust
workspace across all targets and features. These are source dependency inventories,
not exact per-binary SBOMs. Tower's production dependency licenses are included in
`THIRD_PARTY_NOTICES.txt`.

## Container

The workflow builds a Linux x86-64 image at
`ghcr.io/contextosai/contextosd:0.1.0-alpha.6` (also tagged `v0.1.0-alpha.6`), signs
its digest with keyless Sigstore signing and records GitHub build provenance.
The published release's verification evidence records the exact image digest.
Run `towerd` from the same image by selecting `/usr/local/bin/towerd` as its entrypoint.
Supply your configuration and secrets as described in the
[deployment guide](https://github.com/contextosai/ContextOS/blob/v0.1.0-alpha.6/docs/GUIDE.md).

## Alpha limits and support

- Guarantees apply to configured numeric ceilings and mediated tools sharing the
  tenant's protected store. They are opt-in and do not cover tools that bypass it.
- Unknown outcomes block capacity until reconciliation. Recovery from orphaned
  active dispatches remains conservative; do not retry an external effect blindly.
- A resource holds at most 1,024 receipts at once; a settled receipt leaves an hour
  after it is first seen settled, so sustained traffic above roughly 1,024 operations
  an hour on one resource is refused until older receipts age out. A hold
  whose dispatch started but was never observed stays held until reconciled with
  evidence or released by an attestation of absence, which is a principal's audited
  claim, not proof. The peer board is limited to 256 tasks and 1 MiB. Read the [shared-guarantee](https://github.com/contextosai/ContextOS/blob/v0.1.0-alpha.6/docs/SHARED_GUARANTEES.md)
  and [peer-coordination](https://github.com/contextosai/ContextOS/blob/v0.1.0-alpha.6/docs/PEER_COORDINATION.md) limits before integration.
- The legacy ICU comparator stays pinned to preserve existing compiler hashes.
  Upgrading its collation data requires an encoding migration.
- Alpha fixes land on `main` and in subsequent releases; old tags are not patched
  in place. There is no support SLA. Test backups, restore and your provider's
  reconciliation behavior before considering production use.
