# ContextOS 0.1.0-alpha.20

The twentieth alpha of ContextOS. It is a fixes-only release from the fourteenth
review of the runtime, covering the consequential-tool gate (alpha.18) and the
identity and evidence work (alpha.19). It adds no features. The most important fix is
that intent keys now hold across retries. Upgrade before relying on them for
money-moving recovery.

## What changed since 0.1.0-alpha.19

**Intent keys**

- A retried operation claims its intent again before it is sent. Before, only an
  operation's first attempt claimed it. A retry after the provider definitively did
  not apply the effect could therefore send while another run held the same request,
  and both runs' effects could apply. A retry is now refused with
  `effect_repeated_across_runs` while another run holds the request. It goes ahead
  when nobody does.
- When reconciliation, an attestation of absence or crash recovery records an effect
  not applied, the operation's intent claim is released. A stuck request can then be
  redelivered into a new run instead of being refused until `window_seconds` lapse
  (one day by default).

**Erasure**

- Erasure, on request and by retention, now removes a run's delegation chain (the
  user's id, the actors and the user's roles) from its admission record. Before, these
  outlived the erasure. The removal is listed in `run_data_erased` as
  `delegation_chain`, and the record is marked `delegation_chain_erased`.

**Guards and Tower**

- Circuit breakers that count `effects` count only calls handed to the provider. A
  call refused after its attempt was reserved (intent claim, effect claim, task
  limits, shared guarantee, dispatch gate) spent nothing, and can no longer trip a
  breaker or, with `trip = "revoke"`, revoke the agent.
- Approval timeouts: a write racing the timeout mark is re-read and the mark retried,
  instead of `approval_timed_out` being audited again on the next sweep.
- Tower sign-in: the identity provider's token response is capped at 1 MiB like its
  metadata and key set. The endpoints its metadata names (`authorization_endpoint`,
  `token_endpoint`, `jwks_uri`) must be HTTPS unless the issuer itself is plain HTTP,
  which is allowed only in development.

## Upgrading

- **Intent claims on retries.** A retry that alpha.19 would have sent is refused
  (`effect_repeated_across_runs`, obligation `reconcile_existing_operation`) while
  another run holds the request. Treat it like the same refusal of a new operation.
- **New stored documents.** Each intent claim also writes a small pointer document
  per operation (`intent_claim` kind, id prefixed `op:`), holding only the run,
  operation and intent digest. No migration is needed.
- **Fewer breaker trips.** Calls refused before dispatch no longer count toward
  `effects` breakers. Thresholds tuned against alpha.19 may now trip later.
- **Tower SSO.** If an HTTPS issuer's metadata names a plain-HTTP endpoint, Tower now
  refuses that metadata and loads no keys from it, so SSO sign-in fails until the
  identity provider is fixed. API keys keep working.
- Replica clocks must be synchronized (NTP or equivalent). Intent-claim and
  circuit-breaker windows are timed by each replica's clock, as pack-binding leases
  already were.
- No configuration key, API route or storage format is removed.

## Known limits

The known limits of alpha.19 apply unchanged. In addition, an `approval_timed_out`
entry can still be written twice if a replica crashes between the audit and the
mark. That is by design: the timeout is never left unaudited.
